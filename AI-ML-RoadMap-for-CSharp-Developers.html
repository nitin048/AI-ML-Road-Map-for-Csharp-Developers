1 What is AI and ML? Theory

Intuition

Artificial Intelligence (AI) is the umbrella goal: make machines do things that normally require human intelligence — recognising a face, translating a sentence, driving a car. Machine Learning (ML) is the most successful technique for reaching that goal. Instead of a programmer hand-writing every rule, the machine discovers the rules from examples.

Detail — the inversion that changes everything

As a C# developer you normally write the rules yourself:

// Classic programming: YOU write the logic
decimal EstimatePrice(int area, int bedrooms) {
    if (area > 2000 && bedrooms >= 4) return 500_000;
    if (area > 1000) return 300_000;
    return 150_000;   // brittle, hand-tuned, never quite right
}

ML flips the arrows. You give the machine data + answers, and it produces the rules (a model):

The nested hierarchy
  • AI ⊃ ML ⊃ Deep Learning ⊃ LLMs / Generative AI.
  • Not all AI is ML (old chess engines were hand-coded rules). Not all ML is deep learning (linear regression isn't a neural net).
  • ChatGPT = generative AI = deep learning = ML = AI (all four labels true at once).
When to use ML vs plain code
Use plain code when…Use ML when…
Rules are known & stable (tax calc)Rules are unknown or too many to write (spam)
You need exact, auditable logic"Good enough" statistical answers are fine
Little/no historical dataYou have lots of labelled examples
GotchasML is probabilistic, not exact — it will be wrong sometimes, by design. It needs representative data; a model trained only on luxury homes will mis-price a studio. And it can't explain why as clearly as an if.

2 How do Humans Learn? Features and Labels Theory

Intuition

A child learns the letter A not from a definition but from many examples. Each example has observable characteristics (two slanted strokes, a crossbar) and a name ("A"). Machines learn the same way, with precise vocabulary:

  • Feature (X) = a measurable input describing the thing.
  • Label (y) = the correct answer we want to predict.
  • A sample / row = one example = its features + its label.
Detail — turning an image into numbers

This is the pivotal leap of the whole field: a picture becomes a row of numbers. A grayscale image is a grid of brightness values (0 = black, 255 = white). Flatten the grid row-by-row into one long vector, append the label:

The CSV that every dataset looks like
alphabet.csv
px1,px2,px3,px4, ... ,px25,label
0,255,0,255,0, ... ,0,A
255,255,0,0,255, ... ,255,B
0,0,255,255,0, ... ,0,A

Each row is one training example: 25 features + 1 label. Colour images add channels (R,G,B) so a 28×28 colour image is 28·28·3 = 2352 features. Numbers, images, audio, text — all become feature vectors. That's why the next lesson (FLATM) and Lesson 16 ("everything is a vector") work universally.

AnalogyFeatures are the questions on a form; the label is the conclusion at the bottom. Training = reading thousands of filled forms until you can predict the conclusion from the answers.
GotchasNever mix the label into your features (called leakage) — the model will "cheat" in training and fail in production. Also keep feature order consistent between training and inference.
ExerciseHow many features does a 16×16 grayscale digit image have? A 16×16 RGB image? Answer: 256; and 256×3 = 768.

Intuition

5 Algorithm (Formula) vs Model Theory

Intuition

Beginners blur these two. Keep them razor-sharp:

Algorithm = the recipe

A general procedure with unknown coefficients and a rule for choosing them. Linear regression's algorithm is the template y = w·x + b plus "choose w,b to minimise squared error." No numbers yet. Reusable across any dataset.

Model = the baked cake

The algorithm after training filled in the numbers: y = 0.2·x + 0. Frozen, specific to your data, ready to predict. This is what you save to disk and ship.
Detail
AlgorithmModel
Contains numbers?No (parameters unknown)Yes (parameters fitted)
Depends on your data?NoYes — encodes it
Reusable?On any datasetOnly for its trained purpose
In ML.NETTrainers.Sdca(...)the ITransformer from .Fit()
AnalogyCake recipeThe actual baked cake

You train once (bake) and serve many predictions (slices). Two models trained by the same algorithm on different data are completely different models.

Gotchas"I trained the algorithm" is loose talk — you train with an algorithm to produce a model. Precision here prevents confusion later when we swap algorithms but keep the same FLATM shape.
ExerciseYou train SDCA on Mumbai house prices and again on Delhi prices. How many algorithms and how many models exist? Answer: one algorithm, two models.

6 Defining Regression Theory

Intuition

Regression predicts a continuous number — a price, temperature, delay in minutes, tomorrow's index value. Contrast with classification, which predicts a category (spam/not, cat/dog/bird).

QuestionTask
"How much will this house sell for?"Regression (number)
"Will this customer churn?"Binary classification (yes/no)
"Which of 26 letters is this?"Multiclass classification
"How many units will we sell next month?"Regression
Detail — the math you actually need

A trained regression model is a weighted sum: one weight per feature, plus a bias (intercept).

ŷ = w₁·x₁ + w₂·x₂ + ... + wₙ·xₙ + b
    │         │                    └ bias (baseline when all x = 0)
    │         └ contribution of feature 2
    └ how strongly feature 1 pushes the prediction
  • Simple regression: one feature → ŷ = w·x + b (a line).
  • Multiple regression: many features → a plane/hyperplane.
  • Training's job = find the w's and b that make predictions closest to the real labels (smallest error, Lesson 14).
Reading weightsA positive weight means "more of this feature → bigger prediction." A near-zero weight means "this feature barely matters." Inspecting weights is your first feature-importance tool.
GotchasRegression assumes the relationship is (roughly) linear in the features. If it curves, either engineer features (Lesson 17) or use a non-linear algorithm (trees). Also scale features so one large-range feature (income) doesn't swamp a small one (bedrooms).
ExerciseIs "predict the star rating (1–5) a user gives" regression or classification? Both views are valid — treat as regression if you want 3.7-style outputs, or ordinal classification for discrete stars. This ambiguity is real and worth discussing.

7 Simplest ML.NET Regression Code Lab 2

Three concepts that define every ML.NET program
  • MLContext — the single entry point / factory (think DbContext for ML). Seed it for reproducibility.
  • IDataView — a lazy, columnar dataset (like IEnumerable that knows column names + types).
  • Pipeline — transforms + a trainer, composed with .Append(...), executed by .Fit(...).

("MKL components" = Intel Math Kernel Library, the fast native linear-algebra library ML.NET's Ols trainer uses.)

Complete runnable program
Program.cs (dotnet new console; dotnet add package Microsoft.ML)
using Microsoft.ML;
using Microsoft.ML.Data;

public class HouseData {
    [LoadColumn(0)] public float Area;
    [LoadColumn(1)] public float Price;   // this is the Label
}
public class Prediction {
    [ColumnName("Score")] public float Price;  // regression output column is always "Score"
}

class Program {
    static void Main() {
        var ml = new MLContext(seed: 0);            // seed → reproducible

        var houses = new[] {
            new HouseData{ Area=1000, Price=200 },
            new HouseData{ Area=1500, Price=300 },
            new HouseData{ Area=2000, Price=400 },
            new HouseData{ Area=2500, Price=500 },
        };
        IDataView data = ml.Data.LoadFromEnumerable(houses);

        // F: build the Features column | A: pick the SDCA trainer
        var pipeline = ml.Transforms.Concatenate("Features", nameof(HouseData.Area))
            .Append(ml.Regression.Trainers.Sdca(labelColumnName: nameof(HouseData.Price)));

        var model = pipeline.Fit(data);              // T: training

        var engine = ml.Model.CreatePredictionEngine<HouseData, Prediction>(model);
        var p = engine.Predict(new HouseData{ Area = 1750 });
        Console.WriteLine($"Predicted price for 1750 sqft: {p.Price:F1}");  // inference
    }
}
OutputPredicted price for 1750 sqft: 350.0 (SDCA may print ~349.9–350.1 — it's iterative).
Line-by-line
LineFLATMWhat it does
LoadFromEnumerabledataWraps your objects as an IDataView (lazy).
Concatenate("Features", ...)FMerges chosen columns into one vector column named "Features".
Sdca(labelColumnName)A + LChooses the algorithm and names the label column.
Fit(data)TRuns the pipeline; returns the model.
engine.Predict(...)MInference on a single new sample.
Gotchas(1) Column names are strings — a typo like "Featurs" compiles but crashes at Fit. (2) ML.NET regression always outputs a column called "Score"; your prediction class must map to it via [ColumnName("Score")]. (3) float, not double — ML.NET features are 32-bit.
ExerciseChange the trainer to ml.Regression.Trainers.Ols(...) (add package Microsoft.ML.Mkl.Components). Re-run. Do you get exactly 350? OLS is closed-form so it lands cleanly on 350.

8 A Model is a Mathematical Formula Lab 3

Goal

De-mystify "the model" by extracting its actual numbers. There is no magic inside — just weights and a bias.

add to Program.cs after Fit(...)
using Microsoft.ML.Trainers;

// Reach into the trained transformer to read the linear parameters
var linear = ((ISingleFeaturePredictionTransformer<object>)model.LastTransformer)?.Model
             as LinearRegressionModelParameters;
// Simpler, version-robust way:
var lin = (model as TransformerChain<ITransformer>)!
    .LastTransformer as RegressionPredictionTransformer<LinearRegressionModelParameters>;

Console.WriteLine($"bias (b)   = {lin.Model.Bias:F4}");
foreach (var w in lin.Model.Weights)
    Console.WriteLine($"weight (w) = {w:F4}");

// Reproduce the model by hand — no ML.NET needed for inference:
float area = 1750;
float manual = lin.Model.Weights[0] * area + lin.Model.Bias;
Console.WriteLine($"manual prediction = {manual:F1}");
Outputbias (b) = 0.0000 · weight (w) = 0.2000 · manual prediction = 350.0

The "model file" you save with ml.Model.Save(...) is essentially these numbers plus metadata about the transforms. Inference is one multiply and one add per feature — that's why it's so cheap (Lesson 9).

Why this mattersReading weights is your first, free interpretability tool. Big positive weight = strong positive driver; near-zero = ignorable feature (candidate to drop, Lesson 19).
GotchasWeights are only directly comparable if features are on the same scale — normalise first (Lesson 19), otherwise a weight of 0.0001 on "income" may matter more than 5.0 on "bedrooms".

9 Inference vs Training Theory

Intuition

Training = studying for the exam (slow, done once, needs the answer key). Inference = answering a question in the exam (fast, done constantly, no answer key — that's what you're producing).

TrainingInference
FrequencyOnce, or periodically (nightly/weekly)Every prediction request
Needs labels?Yes (it learns from answers)No (it predicts the answer)
CostHigh — CPU/GPU, minutes to daysLow — microseconds, a few multiplies
OutputA model (weights)A prediction (a number/label)
ML.NETpipeline.Fit(data)engine.Predict(x) / model.Transform(batch)
Detail — the production pattern

In a web API: load the model once at startup (or inject a pooled PredictionEnginePool), then call Predict on each request. PredictionEngine is not thread-safe — use Microsoft.Extensions.ML's PredictionEnginePool in ASP.NET.

The #1 architecture bugAccidentally calling Fit() inside a request handler — retraining on every HTTP call. Symptoms: huge latency, memory spikes, non-deterministic answers. Train offline, infer online.
ExerciseIn an ASP.NET app that predicts prices, where should Fit() live and where should Predict() live? Fit: an offline job/CLI that writes model.zip. Predict: a singleton PredictionEnginePool called per request.

11 The Psychology of the ML.NET Code Pipeline Theory

Intuition

ML.NET pipelines feel alien to C# developers because they are declarative and lazy, not imperative. You describe a sequence of transforms; nothing runs until Fit. This is exactly like LINQ: data.Where(...).Select(...) builds a plan; enumeration executes it.

Detail — a pipeline is a conveyor belt
pipeline = transform1      // e.g. NormalizeMinMax
    .Append(transform2)    // e.g. OneHotEncoding
    .Append(transform3)    // Concatenate into "Features"
    .Append(trainer);      // the algorithm
// NOTHING has executed yet — this is just a plan
model = pipeline.Fit(data);// NOW every station runs, in order
The killer feature: train/serve symmetry

The same pipeline definition is reused at inference, so training and serving apply identical preprocessing. If training normalised income, inference normalises income the same way automatically. This eliminates a whole class of "works in the notebook, breaks in prod" bugs.

Gotchas(1) Column-name strings flow between stations ("Features", "Label", "Score", "PredictedLabel") — typos are silent until Fit. (2) Order matters: normalise before concatenate, encode categoricals before concatenate. (3) A transform that "learns" (like Normalize computing min/max) also needs Fit — that's why the whole chain is fit together.
ExerciseReorder a pipeline so Concatenate comes before OneHotEncoding. What happens and why? It fails/misbehaves — the categorical column isn't numeric yet when concatenated. Encode first.

12 Multi-Features Example & Algorithm Confusion Lab 4

Goal

Go from one feature to many, and confront "algorithm confusion" — the beginner realisation that ML.NET offers a dozen trainers that all solve the same shape of problem.

Program.cs (excerpt)
public class House {
    [LoadColumn(0)] public float Area;
    [LoadColumn(1)] public float Bedrooms;
    [LoadColumn(2)] public float Age;
    [LoadColumn(3)] public float Price;
}

var pipeline = ml.Transforms.NormalizeMinMax("Area")
    .Append(ml.Transforms.NormalizeMinMax("Bedrooms"))
    .Append(ml.Transforms.NormalizeMinMax("Age"))

        nameof(House.Area), nameof(House.Bedrooms), nameof(House.Age)))
    .Append(ml.Regression.Trainers.Sdca(labelColumnName: "Price"));

13 OLS vs SDCA Lab 5

Two ways to solve the same line

OLS — Ordinary Least Squares

Solves for the weights in one closed-form matrix equation (the "normal equations", w = (XᵀX)⁻¹Xᵀy) using Intel MKL.
+ Exact, fast on small/medium data, gives statistical extras (p-values).
− Inverting XᵀX is expensive/unstable with many features or collinear features.

SDCA — Stochastic Dual Coordinate Ascent

An iterative optimiser that repeatedly nudges weights toward lower error over many passes.
+ Scales to millions of rows/features, supports L1/L2 regularisation, streaming-friendly.
− Approximate (tiny run-to-run variation), needs enough iterations to converge.
Run both, compare

14 R² and RMSE Lab 6

Intuition

A model is only as good as its measured error on data it hasn't seen. Two core regression metrics:

MetricQuestion it answersRange / goal
RMSE (Root Mean Squared Error)"Typically, how far off am I, in the label's units?"0 = perfect; lower is better; same units as label (e.g. ₹'000)
R² (R-squared)"What fraction of the variation did I explain?"1 = perfect, 0 = no better than predicting the mean, can go negative
The math, briefly
RMSE = sqrt( mean( (yᵢ − ŷᵢ)² ) )      # average squared miss, square-rooted back to units
R²   = 1 − ( Σ(yᵢ−ŷᵢ)²  /  Σ(yᵢ−ȳ)² )  # 1 minus (your error / error of just guessing the mean)
Always evaluate on held-out data
Program.cs (excerpt)
var split = ml.Data.TrainTestSplit(data, testFraction: 0.2, seed: 0);
var model = pipeline.Fit(split.TrainSet);
var scored = model.Transform(split.TestSet);          // predictions on unseen rows
var m = ml.Regression.Evaluate(scored, labelColumnName: "Price");
Console.WriteLine($"R^2  = {m.RSquared:F3}");
Console.WriteLine($"RMSE = {m.RootMeanSquaredError:F2}");
Console.WriteLine($"MAE  = {m.MeanAbsoluteError:F2}");   // avg absolute miss (less outlier-sensitive)
Output (example)R^2 = 0.987 · RMSE = 11.42 · MAE = 9.08 — "on average we're ~₹11k off, explaining 98.7% of price variation."
Gotchas(1) A high R² on training data is meaningless — it can memorise (overfit). Always report test metrics. (2) RMSE punishes big misses more than MAE (squared) — if a few huge errors matter, watch RMSE; if not, MAE is more intuitive. (3) For time series, split chronologically, never randomly (Nifty project).
ExerciseTrain on the full data and evaluate on the same data (no split). Then do a proper split. Compare R². The gap is your overfitting warning sign.

16 Everything is a Vector Theory

Intuition

A vector is just an ordered list of numbers: [1000, 3, 12]. The moment you accept that every input — a house, an image, a sentence — becomes a vector, all of ML turns into geometry.

  • A row of features is a point in n-dimensional space (3 features → a point in 3D).
  • Similar things sit close together; different things sit far apart.
  • Regression fits a line/plane through the points; clustering groups nearby points; embeddings place words as points.
Detail — the operations you'll reuse everywhere

17 OLS with Polynomial Data Lab

Intuition

Real relationships bend. If price grows with area², a straight line underfits. The trick: keep the linear algorithm but engineer curved features (Area², Area³). The model stays "linear in its features" while fitting a curve in the original variable.

Program.cs (excerpt)
public class Row { public float Area; public float Area2; public float Price; }

// Build Area2 from Area with a custom mapping BEFORE concatenating
[CustomMappingFactoryAttribute("poly")]
class PolyMap : CustomMappingFactory<Row,Row> {
    public override Action<Row,Row> GetMapping() => (i,o) => { o.Area = i.Area; o.Area2 = i.Area*i.Area; o.Price = i.Price; };
}

var pipe = ml.Transforms.CustomMapping(new PolyMap().GetMapping(), "poly")
    .Append(ml.Transforms.Concatenate("Features", "Area", "Area2"))

EffectThe fitted model is now price ≈ w1·area + w2·area² + b — a parabola. On curved data its R² jumps well above the straight-line fit.

Linear

Non-linear

22 Clustering Algorithms & KMeans Theory

Intuition

Clustering groups similar points without labels. KMeans is the classic, and it's pure geometry (Euclidean distance from Lesson 18).

The algorithm, step by step
  1. Pick k (number of clusters).
  2. Place k centroids at random positions.
  3. Assign: each point joins its nearest centroid.
  4. Update: move each centroid to the mean of its assigned points.
  5. Repeat 3–4 until centroids stop moving (convergence).
Choosing k — the elbow method

Run KMeans for k = 1,2,3,…; plot the total within-cluster distance. It drops sharply then flattens — the "elbow" is a good k.

Gotchas(1) KMeans uses Euclidean distance → scale your features first or the largest-range feature dominates. (2) Random init can give different results — run several times (ML.NET does this). (3) It assumes roughly round, similar-size clusters; odd shapes need DBSCAN/hierarchical instead.
ExerciseYou cluster customers on age (0–90) and income (0–2,000,000) without scaling. Which feature dominates and why? Income — its raw distances dwarf age. Normalise both first.

23 What is an MLP (Multi-Layer Perceptron)? Theory

Intuition

An MLP is the simplest neural network: layers of "neurons" where each neuron computes a weighted sum + a non-linear activation. Stacking layers lets it learn curves and interactions a single regression can't.

What one neuron does
output = activation( w₁·x₁ + w₂·x₂ + ... + b )
                     └──── same weighted sum as regression ────┘
activation examples:  ReLU(z) = max(0, z)      sigmoid(z) = 1/(1+e⁻ᶻ)

Without the non-linear activation, stacking layers would collapse back into one big linear model — the activation is what gives the network its power to bend.

How it learns: backprop + gradient descent
  1. Forward pass: push inputs through to get a prediction.
  2. Loss: measure error vs the true label.
  3. Backward pass (backprop): compute how each weight contributed to the error (gradients).
  4. Step: nudge every weight a little in the direction that lowers error. Repeat for many epochs.
BridgeThis is the exact loop you'll write by hand in PyTorch (L53–54): forward → loss → backward() → step(). Transformers (L24) are elaborate neural nets trained the same way.
ExerciseAn MLP with layers 10 → 64 → 1 (ignoring biases) has how many weights? 10×64 + 64×1 = 640 + 64 = 704.

What "attention" actually does (intuition)

For each token, attention asks "which other tokens should I look at to understand myself?" and computes a weighted blend of their vectors. 45 Word Embeddings with GloVe 50D + Cosine / Euclidean Similarity Lab

The idea in one paragraph

TF-IDF (L44) still treats "car" and "automobile" as unrelated because they're different strings. Word embeddings fix this by giving every word a dense vector of real numbers, learned so that words used in similar contexts land near each other in space. GloVe ("Global Vectors", Stanford) is a pretrained set of such vectors. The 50D file (glove.6B.50d.txt) gives each of ~400,000 words a 50-number vector. Once words are vectors, "similarity" becomes a geometry question you already know how to answer (L18): cosine or Euclidean distance.

What the data file looks like

Each line is a word followed by 50 floats, space-separated:

glove.6B.50d.txt (excerpt)
the 0.418 0.24968 -0.41242 0.1217 0.34527 ... (50 numbers)
king 0.50451 0.68607 -0.59517 0.020485 ... (50 numbers)
queen 0.37854 1.8233 -1.2648 -0.1043 ... (50 numbers)
Why cosine, not Euclidean, for text

Euclidean distance grows if one vector simply has a bigger magnitude (a longer document, a more "intense" word). For meaning we care about direction, not length — two vectors pointing the same way are semantically similar even if one is longer. Cosine measures the angle:

cosine(a, b) = (a · b) / (‖a‖ · ‖b‖)
   where  a · b  = Σ aᵢ·bᵢ           (dot product)
          ‖a‖    = √(Σ aᵢ²)          (vector length / L2 norm)
result range: -1 (opposite) … 0 (unrelated) … 1 (same direction)
Worked example (2-D so you can see the numbers)

Let a = [3, 4] and b = [4, 3]. Dot = 3·4 + 4·3 = 24. ‖a‖ = √(9+16) = 5, ‖b‖ = 5. Cosine = 24 / (5·5) = 0.96 (very similar direction). Euclidean = √((3−4)² + (4−3)²) = √2 ≈ 1.41. Notice cosine says "almost identical direction" while Euclidean reports a non-trivial gap — different questions, different answers.

def cosine(a, b):

def euclidean(a, b):
    return float(np.linalg.norm(a - b))

46 A Simple BERT Example Lab

Why BERT beats GloVe

GloVe is static: one vector per word forever. BERT (Bidirectional Encoder Representations from Transformers) is contextual: it reads the whole sentence and produces a different vector for a word depending on its neighbours. "bank" in "river bank" and "bank" in "central bank" get different vectors. BERT is an encoder-only transformer (L24) trained to understand text — ideal for search, classification, clustering, and semantic similarity. (It does not generate text; that's GPT's job, L47.)

How BERT turns text into vectors
  1. Tokenize with WordPiece: "embeddings" → ["em", "##bed", "##ding", "##s"]. Special tokens [CLS] (start) and [SEP] (end) are added.
  2. Encode through 12 (base) transformer layers using self-attention — every token attends to every other.
  3. Read out either the [CLS] vector or the mean of all token vectors as the sentence embedding (typically 384 or 768 numbers).

47 GPT with Offline Encoding Lab Concept demo

The one loop that is all of GPT

GPT is a decoder-only transformer trained on one objective: predict the next token. Text generation is just that prediction run in a loop — append the predicted token and predict again:

What "offline encoding" means

Before the model sees text, a tokenizer converts characters to integer ids using a fixed vocabulary shipped in files (e.g. vocab.json + merges.txt for GPT-2's byte-pair encoding). "Offline" = you run that tokenizer locally, no API call, purely a lookup + merge algorithm.

Concept pseudocode (does not run as-is)
gpt_generate_demo.py (illustrative)
# CONCEPT ONLY — assumes a loaded local model + tokenizer
tokens = tokenizer.encode("The capital of France is")   # e.g. [464, 3139, 286, 4881, 318]

for _ in range(5):
    logits = model.forward(tokens)          # shape: [vocab_size] scores for the NEXT token
    probs  = softmax(logits / temperature)  # temperature: 0 = greedy, higher = more random
    next_id = sample(probs)                  # or argmax(probs) for greedy
    tokens.append(next_id)
    if next_id == tokenizer.eos_id: break

print(tokenizer.decode(tokens))              # "The capital of France is Paris"

StrategyWhat it doesEffect
Greedy (temp 0)Always pick the highest-probability tokenDeterministic, can be repetitive
TemperatureFlatten/sharpen the probability curveHigher = more creative/random
Top-kSample only from the k most likelyCuts off nonsense tail
Top-p (nucleus)Sample from the smallest set whose probs sum to pAdaptive diversity

49 Simple RAG Demonstration Lab

RAG (Retrieval-Augmented Generation) solves the LLM's two biggest weaknesses at once: it doesn't know your private data, and it hallucinates when asked about things outside its training. RAG fixes both by retrieving relevant snippets of your own data at query time and pasting them into the prompt as grounding context. The model then answers from the provided text rather than from memory.

The six-stage pipeline

Stages 1–3 happen once (indexing). Stages 4–6 happen on every query. The only new idea versus what you already learned: we reuse embeddings (L45) and cosine similarity (L18) to find the right context.

A complete, self-contained RAG in C# (no external vector DB)

This runs entirely in memory so you can see every moving part. In production you'd swap the list for a vector database (Azure AI Search, Qdrant, Postgres+pgvector) and the fake embedder for a real one (Azure OpenAI text-embedding-3-small, or a local ONNX MiniLM model from L46/L55).

using System;
using System.Collections.Generic;
using System.Linq;

// --- A chunk = a slice of a document + its embedding vector ---
record Chunk(string Text, float[] Vector, string Source);

class TinyRag
{
    private readonly List<Chunk> _store = new();

    // STAGE 1-3: index documents
    public void Index(string source, string text, Func<string,float[]> embed)
    {
        foreach (var chunk in Split(text, size: 200, overlap: 40))   // L50
            _store.Add(new Chunk(chunk, embed(chunk), source));
    }

    // STAGE 4-5: retrieve the top-k most similar chunks to the query
    public List<Chunk> Retrieve(float[] queryVec, int k = 3) =>
        _store.OrderByDescending(c => Cosine(c.Vector, queryVec)).Take(k).ToList();

    // STAGE 6 would call the LLM; here we just build the grounded prompt
    public string BuildPrompt(string question, List<Chunk> ctx)
    {
        var context = string.Join("\n---\n", ctx.Select(c => $"[{c.Source}] {c.Text}"));
        return $"""
            You are a support bot. Answer ONLY from the context below.
            If the answer is not in the context, say "I don't know".

            Context:
            {context}

            Question: {question}
            """;
    }

    static float Cosine(float[] a, float[] b)
    {
        float dot = 0, na = 0, nb = 0;
        for (int i = 0; i < a.Length; i++){ dot += a[i]*b[i]; na += a[i]*a[i]; nb += b[i]*b[i]; }
        return dot / (MathF.Sqrt(na) * MathF.Sqrt(nb) + 1e-8f);
    }

    static IEnumerable<string> Split(string t, int size, int overlap)
    {
        for (int i = 0; i < t.Length; i += size - overlap)
            yield return t.Substring(i, Math.Min(size, t.Length - i));
    }
}
Expected behaviourAsk "What is the refund window?" and RAG retrieves the chunk containing your refund policy, so the LLM answers "30 days" with a citation. Ask "What is the capital of Mars?" and — because no chunk matches — it answers "I don't know" instead of hallucinating. That grounding is the whole point.
Why each design choice matters
ChoiceWhy
Cosine, not EuclideanEmbeddings encode meaning as direction (L18/L45); length is irrelevant.

Common failure modes
  • Retrieval miss — the right chunk isn't in top-k. Fix: better chunking (L50), a stronger embedder, or a hybrid keyword+vector search.
  • Context overflow — you stuff too many chunks and blow the token limit. Fix: cap k, summarise, or re-rank.
  • Stale index — docs changed but embeddings weren't rebuilt. Fix: re-index on change.
  • Wrong distance metric — using Euclidean on un-normalised embeddings gives poor ranking.
TakeawayRAG = search + prompt. Retrieve with embeddings + cosine, then instruct the LLM to answer only from what you retrieved. It is the single most useful pattern for putting an LLM on top of your own data — and exactly how the perf-goals AI assistant grounds its answers.

Chunking is how you cut documents into the pieces you embed and retrieve. It is the highest-leverage knob in RAG: the fanciest LLM can't answer from a chunk that was split badly. The goal of every strategy is the same — each chunk should be self-contained enough to answer a question yet small enough to retrieve precisely.

Graph-based chunking with Neo4j (why & shape)

Pure vector search can miss answers that require connecting facts across documents ("who approved the goal that references policy X?"). A knowledge graph stores those links explicitly.

// Cypher: chunks as nodes, relationships as edges
CREATE (c1:Chunk {id:"c1", text:"...", source:"policy.md"})
CREATE (c2:Chunk {id:"c2", text:"...", source:"goals.md"})
CREATE (c2)-[:REFERENCES]->(c1)          // explicit relationship

// retrieve a chunk AND everything it links to
MATCH (c:Chunk)-[:REFERENCES]->(related)
WHERE c.id = "c2" RETURN c, related

This is "GraphRAG": combine vector similarity (find the entry chunk) with graph traversal (pull connected chunks). Overkill for a FAQ, powerful for interconnected corpora.

Chunking pitfalls
  • Too big → retrieval is imprecise and the answer is buried in noise.
  • Too small → chunks lose the context needed to make sense.
  • No overlap → answers split across a boundary become unfindable.
  • Ignoring structure → splitting a table row from its header destroys meaning (use modality-based).
TakeawayStart with recursive + overlap (size 300–800 tokens, 10–20% overlap). Measure retrieval quality on real questions. Only reach for semantic, hierarchical, or graph chunking when measurements say you need it.

52 PyTorch Fundamentals Lab

PyTorch is the framework most deep-learning research and production runs on. As a C# developer, think of it as "LINQ + NumPy for tensors, with automatic calculus." Two features make it powerful: autograd (it computes derivatives for you) and GPU tensors (the same code runs on a graphics card).

The tensor — a NumPy array with superpowers
import torch

a = torch.tensor([[1., 2.], [3., 4.]])   # 2x2 tensor
print(a.shape)      # torch.Size([2, 2])
print(a.dtype)      # torch.float32
print(a @ a)        # matrix multiply
print(a.mean())     # tensor(2.5000)

# move to GPU if available (same code, faster hardware)
device = "cuda" if torch.cuda.is_available() else "cpu"
a = a.to(device)
Expected outputtorch.Size([2, 2]), then torch.float32, then the matrix product [[7,10],[15,22]], then tensor(2.5000).
Autograd — the reason PyTorch exists

Training a neural net means "which direction should I nudge each weight to reduce error?" That direction is the gradient (derivative). PyTorch computes it automatically: set requires_grad=True, do math, call .backward().

x = torch.tensor([2.0], requires_grad=True)
y = x ** 2 + 3 * x + 1      # y = x^2 + 3x + 1
y.backward()                 # compute dy/dx
print(x.grad)             # dy/dx = 2x + 3 = 7  -> tensor([7.])
Expected outputtensor([7.]) — PyTorch differentiated x²+3x+1 to 2x+3 and evaluated it at x=2. You never wrote the derivative; autograd did. Scale this to millions of weights and you have neural-network training.
The universal training loop

Every PyTorch model — regression, MLP, transformer — trains with the same five-line rhythm. Memorise it:

for epoch in range(epochs):
    pred = model(X)              # 1. FORWARD: predict
    loss = loss_fn(pred, y)      # 2. LOSS: how wrong?
    optimizer.zero_grad()        # 3. reset old gradients
    loss.backward()              # 4. BACKWARD: compute gradients (autograd)
    optimizer.step()             # 5. UPDATE weights a tiny step
StepFLATM / plain meaning
forwardRun the current model (inference during training)
lossMeasure error vs the labels (like RMSE, L14)
zero_gradGradients accumulate by default — clear them each step
backwardAutograd fills every weight's .grad
stepOptimizer moves weights downhill (gradient descent)
The #1 beginner bugForgetting optimizer.zero_grad(). Without it, gradients from every epoch pile up and training diverges into NaN. If your loss explodes, check this first.
TakeawayTensor = data. Autograd = automatic calculus. Training loop = forward → loss → zero_grad → backward → step, repeated. Everything in L53–L54 is this loop with a bigger model.

53 Creating a Model in PyTorch — Simple Linear Regression Lab

We now build the full house-price regression from Part 1, but in PyTorch, so you see the training loop learn the weights you earlier read out of ML.NET. Same FLATM, different engine.

Complete, runnable program
import torch
import torch.nn as nn

# F and L: area (feature) -> price (label). price = 0.2 * area (in $1000s)
X = torch.tensor([[1000.], [1500.], [2000.], [2500.]])
y = torch.tensor([[200.],  [300.],  [400.],  [500.]])

# normalise the feature so training is stable (huge inputs blow up gradients)
X = X / 1000.            # now 1.0, 1.5, 2.0, 2.5

model = nn.Linear(1, 1)              # A: y = w*x + b, one weight + bias
loss_fn = nn.MSELoss()               # mean squared error (L14)
opt = torch.optim.SGD(model.parameters(), lr=0.05)

for epoch in range(500):          # T: training loop (L52)
    pred = model(X)
    loss = loss_fn(pred, y)
    opt.zero_grad()
    loss.backward()
    opt.step()
    if epoch % 100 == 0:
        print(f"epoch {epoch:3d}  loss {loss.item():.2f}")

# M: inspect the learned formula
w = model.weight.item(); b = model.bias.item()
print(f"learned: price = {w:.1f} * (area/1000) + {b:.1f}")

# inference on a new house (1750 sqft -> area/1000 = 1.75)
with torch.no_grad():
    print("predict 1750:", model(torch.tensor([[1.75]])).item())
Expected output (approx)Loss falls each epoch (e.g. 90000 → 12 → ~0). Final line: learned: price = 200.0 * (area/1000) + 0.0 and predict 1750: ~350. The model rediscovered the 0.2-per-sqft rule — identical to the Excel trendline (L4) and the ML.NET weights (L8).

54 Creating a Model using Multiple Layers (MLP) Lab

A single Linear can only fit straight lines/planes. Real data curves. Stacking layers with a non-linear activation between them (the MLP from L23) lets the network bend to fit non-linear patterns.

Why one layer isn't enough
Key factTwo Linear layers with nothing between them collapse into one Linear layer (matrix math: A·B is still a single linear map). The ReLU in between is what unlocks non-linearity. No activation = no benefit from depth.
Complete MLP for a non-linear target
import torch, torch.nn as nn

# target is CURVED: y = x^2  (a line can't fit this)
X = torch.linspace(-3, 3, 100).unsqueeze(1)   # shape [100,1]
y = X ** 2

model = nn.Sequential(
    nn.Linear(1, 32), nn.ReLU(),    # hidden layer 1 + activation
    nn.Linear(32, 32), nn.ReLU(),   # hidden layer 2 + activation
    nn.Linear(32, 1)                # output
)
loss_fn = nn.MSELoss()
opt = torch.optim.Adam(model.parameters(), lr=0.01)   # Adam > SGD for MLPs

for epoch in range(2000):
    loss = loss_fn(model(X), y)
    opt.zero_grad(); loss.backward(); opt.step()
    if epoch % 500 == 0:
        print(f"epoch {epoch}  loss {loss.item():.4f}")

with torch.no_grad():
    print("predict x=2 (true=4):", model(torch.tensor([[2.0]])).item())
Expected outputLoss drops from ~4 toward ~0.01. Final prediction for x=2 lands near 4.0 — the network learned the parabola that a single Linear could never fit. That's the power of hidden layers + ReLU.
Anatomy of the network
ComponentRoleKnob to tune
nn.Linear(in,out)Learns a weighted combinationwidth (out features)
nn.ReLU()Adds non-linearity (max(0,x))swap for GELU/Tanh
number of layersDepth = capacitymore = powerful but overfits
AdamAdaptive optimizerlearning rate

Overfitting warningGive it too much capacity (many wide layers) and too many epochs and it will memorise the training points, including noise, then fail on new data. Defences: fewer/narrower layers, nn.Dropout, weight decay, and always checking a held-out test set (L14).
TakeawayDepth + non-linear activations = the ability to approximate almost any function. This exact pattern (linear layers + activations, trained by the L52 loop) scales all the way up to the transformers behind GPT.
ExerciseRemove both nn.ReLU() lines and retrain. The loss will plateau high and the x=2 prediction won't reach 4 — proving that without activations, stacked linear layers are just one linear layer. Put ReLU back and watch it fit.

63 Agentic AI with LangChain / LangGraph (Python) Lab

LangChain is the Python ecosystem for LLM apps (chains, tools, memory, retrievers). LangGraph models an agent as a graph of steps with shared state and loops — ideal for the plan → act → observe → repeat cycle that real agents need. It's the Python counterpart to Semantic Kernel.

A tool-using agent in LangChain
from langchain_openai import ChatOpenAI
from langchain.agents import tool, create_react_agent, AgentExecutor
from langchain import hub

@tool
def open_goal_count(user: str) -> int:
    """Return the number of open goals for a user."""   # docstring = tool description
    return 3 if user == "pkelly" else 0

llm = ChatOpenAI(model="gpt-4o", temperature=0)
prompt = hub.pull("hwchase17/react")          # ReAct reasoning template
agent = create_react_agent(llm, [open_goal_count], prompt)
executor = AgentExecutor(agent=agent, tools=[open_goal_count], verbose=True)

executor.invoke({"input": "How many open goals does pkelly have?"})
Expected trace (verbose=True)You'll see the ReAct loop: Thought ("I should check the goal count") → Action (open_goal_count("pkelly")) → Observation (3) → Final Answer ("pkelly has 3 open goals"). This visible reasoning is why LangChain is great for learning how agents "think."
LangGraph — agents as stateful graphs

For anything beyond one tool call, LangGraph gives explicit nodes, edges, and shared state, so you can build loops with checkpoints (retry, human-in-the-loop, branching):

from langgraph.graph import StateGraph, END
g = StateGraph(dict)
g.add_node("plan", plan_step)
g.add_node("act", act_step)
g.add_conditional_edges("act", lambda s: "act" if s["more"] else END)  # loop
g.set_entry_point("plan")
app = g.compile()
Practical noteSet temperature=0 for agents — you want deterministic tool selection, not creativity. And cap the number of steps: an agent stuck in a bad loop can burn tokens/money fast. LangGraph's explicit edges make loop limits easy to enforce.
TakeawayLangChain = quick tool-using agents with visible ReAct reasoning; LangGraph = production agents as controllable state machines. Same core idea as Semantic Kernel (L62), Python flavour.

65 Data Quality (for Generative AI) Theory

Everything from L27 (descriptive stats, outliers, missing values) still applies to classical ML. Generative/RAG systems add a second kind of data quality: knowledge quality. Bad knowledge in → confidently wrong answers out.

DimensionWhy it breaks RAG/LLM appsFix
Chunk qualityBadly split chunks aren't retrievable or lack contextRecursive + overlap (L50); measure retrieval
DuplicationDuplicate chunks crowd out top-k, wasting the context windowDe-dup before embedding
FreshnessStale docs → outdated answers presented confidentlyRe-index on change; tag with dates

Shift in mindsetFor classical ML, data quality = clean columns and sensible distributions. For generative AI, it = clean, current, well-chunked, well-tagged knowledge plus an eval set to detect regressions. Both obey the same law: garbage in, garbage out.

TakeawayIn GenAI, "data quality" expands from statistics to knowledge hygiene: fresh, de-duplicated, well-chunked, tagged, PII-safe content, verified by evals. It's the unglamorous work that separates a demo from a trustworthy product.

Stage 2 — Retrieval with a FAKE embedder (runs offline, teaches the mechanics)

Before wiring a real model, we prove retrieval with a deterministic fake embedder. It turns text into a tiny vector by counting keyword hits. It's not "smart," but it lets you watch cosine similarity pick the right question with zero cost or network. This isolates the RAG plumbing from the model.

Program.cs (Stage 2)
using InterviewMate;

// A fake "embedder": maps text to a 4-dim vector by counting topic keywords.
// Real embedders output 384-1536 dims of learned meaning; this just teaches the flow.
static float[] FakeEmbed(string text)
{
    text = text.ToLowerInvariant();
    float Has(string w) => text.Contains(w) ? 1f : 0f;
    return new[]{ Has("async")+Has("await")+Has("task"),
                    Has("dependency")+Has("inject")+Has("di"),
                    Has("garbage")+Has("gc")+Has("heap"),
                    Has("c#")+Has(".net") };
}

static float Cosine(float[] a, float[] b)
{
    float dot=0, na=0, nb=0;
    for (int i=0; i<a.Length; i++){ dot+=a[i]*b[i]; na+=a[i]*a[i]; nb+=b[i]*b[i]; }
    return dot / (MathF.Sqrt(na)*MathF.Sqrt(nb) + 1e-8f);   // +epsilon avoids /0
}

// INDEX: precompute a vector for every question (do this once).
var index = QuestionBank.All
    .Select(q => (Question: q, Vector: FakeEmbed(q.Text)))
    .ToArray();

Console.Write("Pick a topic (async / di / gc): ");
var topic = Console.ReadLine() ?? "async";

// RETRIEVE: embed the query, find the highest-cosine question.
var queryVec = FakeEmbed(topic);
var best = index
    .OrderByDescending(x => Cosine(x.Vector, queryVec))
    .First().Question;

Console.WriteLine($"\nRetrieved question:\n{best.Text}");
Expected outputType di and it prints the dependency-injection question; type gc and it prints the garbage-collector question. You just did retrieval (RAG stages 1–5 from L49) with no LLM. Run it a few times with different topics.
LineWhat it does & why
FakeEmbedTurns text → vector. The real one (Stage 3) captures meaning; this counts keywords so the demo is deterministic and offline.
index = ... Select(...)Precomputes one vector per question. In real RAG you store these in a vector DB so you don't re-embed every query.
OrderByDescending(Cosine).First()Top-k with k=1: the closest question by meaning-direction (L18/L45).

Watch it fail on purposeType a topic the fake embedder doesn't know (e.g. threads). Every vector scores ~0, so "best" is arbitrary. That is the real-world "retrieval miss" from L49 — and exactly why Stage 3 swaps in a real embedder that understands meaning beyond keywords.

Stage 5 — Grade the answer (an LLM eval, L61)

This is the heart of the app. We give the model the question, the ideal answer (from the retrieved Question.IdealAnswer), and the candidate's answer, and ask for a structured JSON verdict. This is exactly the "LLM-as-judge" evaluation pattern from L61 — applied per answer.

Program.cs (Stage 5 — grade prompt + parse)
using System.Text.Json;

var gradePrompt = $"""
    You are grading a C# interview answer. Compare the CANDIDATE answer
    to the IDEAL answer. Score 0-10 for correctness and completeness.
    Be fair but strict; ignore wording differences, judge the concepts.

    QUESTION: {best.Text}
    IDEAL: {best.IdealAnswer}
    CANDIDATE: {candidateAnswer}

    Return ONLY valid JSON, no markdown fences, exactly:
    {"score": <0-10 integer>, "missing": ["..."], "feedback": "one short paragraph"}
    """;

var gradeResponse = await chat.GetResponseAsync(gradePrompt);
var json = StripFences(gradeResponse.Text);      // defend against ```json fences

try
{
    using var doc = JsonDocument.Parse(json);
    var root  = doc.RootElement;
    int score = root.GetProperty("score").GetInt32();
    string fb = root.GetProperty("feedback").GetString() ?? "";

    Console.WriteLine($"\nScore: {score}/10");
    Console.WriteLine($"Feedback: {fb}");
    foreach (var m in root.GetProperty("missing").EnumerateArray())
        Console.WriteLine($"  - missing: {m.GetString()}");
}
catch (JsonException)
{
    Console.WriteLine("Could not parse grader output. Raw:\n" + json);
}

// The fence-stripper: models love to wrap JSON in ```json ... ``` (L51).
static string StripFences(string raw)
{
    var t = raw.Trim();
    if (t.StartsWith("```"))
    {
        int nl = t.IndexOf('\n');
        if (nl >= 0) t = t[(nl+1)..];
        if (t.EndsWith("```")) t = t[..t.LastIndexOf("```")].TrimEnd();
    }
    return t;
}
Expected outputGive a good answer → Score: 8/10 with encouraging feedback and maybe one missing point. Give a wrong answer → Score: 2/10 with the missing concepts listed. Give an empty answer → Score: 0/10. The grade tracks answer quality, which means the eval is working.
Design decisionWhy
Include the IDEAL answerGives the judge a reference (L61 "similarity"). Without it, grading is subjective and inconsistent run-to-run.
"Return ONLY valid JSON"Makes the output machine-parseable. This one line is doing real integration work (L51).
StripFencesReal models still wrap JSON in code fences. The perf-goals codebase has the exact same helper. Defensive parsing prevents crashes.
try/catch (JsonException)LLM output is untrusted (L67). Never assume it parses; degrade gracefully and show the raw text for debugging.
Reliability tipsPrefer the provider's native JSON mode/structured-output feature when available — it guarantees valid JSON and removes the need for StripFences. Also set a low temperature for grading (you want consistent scores, not creativity). If scores swing wildly on re-runs, that's your signal to lower temperature and tighten the rubric.
MilestoneYou now have a working single-question interviewer: retrieve → ask → answer → grade. That is a complete generative feature. Stages 6–7 turn it into an agent and add persistence + evaluation of the app itself.
Stage 6 — Turn it into an agent (Semantic Kernel tools, L62)

Right now you orchestrate the steps in code. An agent lets the LLM decide when to call your functions (save a score, fetch the next question). We expose two C# methods as tools and let Semantic Kernel auto-invoke them.

InterviewPlugin.cs
using System.ComponentModel;
using Microsoft.SemanticKernel;

public class InterviewPlugin
{
    private readonly ScoreStore _store;   // from Stage 7
    public InterviewPlugin(ScoreStore store) => _store = store;

    [KernelFunction, Description("Save a candidate's score for a topic (0-10).")]
    public string SaveScore(
        [Description("topic key, e.g. async")] string topic,
        [Description("score 0-10")] int score)
    {
        _store.Save(topic, score);
        return $"Saved {score}/10 for {topic}.";
    }

    [KernelFunction, Description("Get the candidate's average score so far.")]
    public double GetAverage() => _store.Average();
}
Program.cs (Stage 6 — build the kernel & let the model call tools)

ElementRole
[Description] textThis is literally how the model "reads" your tool. Vague descriptions → wrong tool choices. Write them like API docs.
AutoInvokeKernelFunctionsThe switch that lets the model actually call the methods (not just suggest them).
Typed parametersSK converts the model's chosen arguments to C# types. Validate them — the model can hallucinate a score of 99.
Agent safety (L62/L67)Auto-invoke means the model triggers real actions. For anything destructive, require confirmation and validate arguments before acting. Here, clamp score to 0–10 inside SaveScore so a hallucinated value can't corrupt your data. Never expose a tool you wouldn't let an untrusted caller run.
Stage 7 — Persistence + evaluating the app itself

Two finishing pieces: store scores so progress survives restarts, and build a small eval set to measure whether your grader is trustworthy (evaluating the evaluator).

ScoreStore.cs (simple JSON persistence)
using System.Text.Json;

public class ScoreStore
{
    private readonly string _path = "scores.json";
    private List<(string Topic, int Score)> _scores = new();

    public ScoreStore()
    {
        if (File.Exists(_path))
            _scores = JsonSerializer.Deserialize<List<(string,int)>>(File.ReadAllText(_path)) ?? new();
    }

    public void Save(string topic, int score)
    {
        score = Math.Clamp(score, 0, 10);       // defend against bad model input
        _scores.Add((topic, score));
        File.WriteAllText(_path, JsonSerializer.Serialize(_scores));
    }

    public double Average() => _scores.Count == 0 ? 0 : _scores.Average(s => s.Score);
}

Step 2 — Turn a price series into supervised rows (feature engineering, L19)

A raw price series isn't a supervised dataset. We must construct rows where the features are things known today and the label is tomorrow's close. This transformation is where the project is won or lost.

Program.cs (Step 2 — build features)
public class Row          // one supervised training example
{
    public float PrevClose;   // close of the PREVIOUS day (lag-1)
    public float Ma5;         // 5-day moving average of close
    public float Ma20;        // 20-day moving average of close
    public float Return1;     // yesterday's 1-day % return
    public float Volatility5; // stddev of last 5 returns
    public float DayOfWeek;   // calendar feature (0-6)
    public float NextClose;   // LABEL: the close we want to predict
}

var rows = new List<Row>();
for (int i = 20; i < bars.Count - 1; i++)   // start at 20 so Ma20 has history; stop 1 early for the label
{
    var last5  = bars.Skip(i-5).Take(5).Select(b => b.Close).ToArray();
    var last20 = bars.Skip(i-20).Take(20).Select(b => b.Close).ToArray();
    var rets   = Enumerable.Range(i-5, 5)
                   .Select(j => (bars[j].Close - bars[j-1].Close) / bars[j-1].Close).ToArray();

    rows.Add(new Row
    {
        PrevClose   = bars[i].Close,
        Ma5         = last5.Average(),
        Ma20        = last20.Average(),
        Return1     = (bars[i].Close - bars[i-1].Close) / bars[i-1].Close,
        Volatility5 = MathF.Sqrt(rets.Select(r => (r - rets.Average())*(r - rets.Average())).Average()),
        DayOfWeek   = (float)DateTime.Parse(bars[i].Date).DayOfWeek,
        NextClose   = bars[i+1].Close      // tomorrow -> the thing we learn to predict
    });
}
Console.WriteLine($"supervised rows: {rows.Count}");
Expected outputsupervised rows: ~479 (500 bars minus the 20-day warm-up and the final day that has no "tomorrow"). Each row now has features known on day i and the label from day i+1.
The cardinal sin: look-ahead leakageEvery feature must use ONLY data available on or before day i. NextClose (day i+1) is the label, never a feature. If you accidentally compute a feature using future bars, your test scores will look amazing and live results will be worthless. This is the single most common way people fool themselves in time-series ML.
ConceptYou just did the hardest part of L19: converting an unstructured series into FLATM shape (features + label). The algorithm choice later matters far less than these features.
Step 3 — Split chronologically + build the baseline (L14)

You cannot judge a model without something to beat. The honest baseline for price prediction is "tomorrow = today" (predict PrevClose as NextClose). Any model that can't beat this is useless. And the split must be chronological — train on the past, test on the most recent slice.

Program.cs (Step 3 — split + baseline)
// CHRONOLOGICAL split: first 80% train, last 20% test. NEVER shuffle time series.
int cut = (int)(rows.Count * 0.8);
var trainRows = rows.Take(cut).ToList();
var testRows  = rows.Skip(cut).ToList();

// BASELINE: predict tomorrow = today's close (PrevClose). Measure its RMSE.
double baselineSqErr = testRows
    .Average(r => Math.Pow(r.NextClose - r.PrevClose, 2));
double baselineRmse = Math.Sqrt(baselineSqErr);
Console.WriteLine($"Baseline RMSE (tomorrow=today): {baselineRmse:F2}");
Expected outputA number like Baseline RMSE (tomorrow=today): 145.30 (units = index points). This is your bar. Every trained model below must produce a lower RMSE on the same test set to have earned its keep.
Why chronological, not randomIf you shuffle and randomly split, some training rows come from after some test rows — the model effectively "sees the future." Scores look great, reality disappoints. Time series is split by time, always.
ConceptMeaning here
BaselineThe dumbest reasonable predictor. Beating it is the minimum bar for "the model learned something."
RMSE (L14)Typical error in index points; lower is better; directly comparable to the models below.
Test slice = most recent 20%Simulates "predict the near future from the past" — what you'd actually do live.
Step 4 — Train a model (ML.NET pipeline, L7/L11)

Build the familiar pipeline: concatenate features → normalize → a regression trainer. We start with SDCA (L13), then compare alternatives in Step 5.

Program.cs (Step 4 — train)
var trainData = ml.Data.LoadFromEnumerable(trainRows);

Step 5 — Evaluate & compare algorithms (L12–L14)

}

Evaluate("SDCA", model);
